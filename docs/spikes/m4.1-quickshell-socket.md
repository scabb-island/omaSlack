# Spike M4.1 — Can Quickshell be a direct client of the daemon socket?

Date: 2026-11-26 · Quickshell 0.3.2 (Omarchy build) · Go 1.26.11 · Result: **yes, without the `ctl --stream` bridge**

## Question

`design.md` left Open Question 1 open: does `Quickshell.Io`'s `Socket` with a `SplitParser` deliver NDJSON lines reliably on a long stream, or do we need a `Process` running `omaslack ctl --stream` as a bridge?

## How it was tested

Code in `spikes/m4-quickshell-socket/`:

- `server/main.go`: a Go server speaking a small JSON-RPC over NDJSON on a 0600 unix socket.
- `client/shell.qml`: a windowless Quickshell config that runs through these phases and prints one `RESULT {json}` line at the end:
  1. **Late start:** the client starts 2 s before the server and retries.
  2. **Burst:** N events as fast as possible. They include accents, emoji, escaped `\n` and quotes, and one in every 2,000 is a 256 KiB line. Count, `seq` order and UTF-8 text bytes are checked against what the server reports.
  3. **Latency:** 200 sequential round-trip pings.
  4. **Interleaving:** the server sends a tick every 5 ms (400 in total) while the client pings every 20 ms.
  5. **Disconnect:** the server closes the connection; the client must notice, reconnect and repeat `hello`.
  6. **Shell freeze:** a 16 ms `Timer` measures the longest event-loop pause during the burst.

To reproduce:

```bash
go build -o /tmp/spike-server ./spikes/m4-quickshell-socket/server
/tmp/spike-server -delay 2s &
QT_QPA_PLATFORM=offscreen quickshell -p spikes/m4-quickshell-socket/client/shell.qml
OMASLACK_SPIKE_BURST=100000 QT_QPA_PLATFORM=offscreen quickshell -p spikes/m4-quickshell-socket/client/shell.qml
```

## Results (on the development machine)

Measured with the original Spanish test strings; the strings were later translated, which changes the byte totals but not the behavior.

| Measurement | 20,000 events | 100,000 events |
|---|---|---|
| Received / requested | 20,000 / 20,000 | 100,000 / 100,000 |
| Out of order | 0 | 0 |
| Parse errors | 0 | 0 |
| Text bytes (client = server) | 3,235,133 | 16,220,117 |
| Longest line | 229,443 characters | 229,443 characters |
| Burst duration | 215 ms | 983 ms |
| Events per second | ~93,000 | ~102,000 |
| **Worst event-loop pause** | **35 ms** | **33 ms** |
| Ping RTT p50 / p99 / max | 0 / 1 / 1 ms | 0 / 1 / 1 ms |

Volume-independent phases (20,000 run):

- **Interleaving:** 400 of 400 ticks arrived, in order. Pings during the interleaving had a p99 of 1 ms.
- **Disconnect:** the client noticed the close in 0 ms and sent `hello` again 252 ms later (the retry timer was 250 ms).
- **Late start:** 9 retries until the socket appeared, then normal operation.

## Conclusions

1. **A direct `Socket` is enough.** The `ctl --stream` bridge is not needed, which saves an extra process per shell. Open Question 1 is closed.
2. **The shell does not freeze.** The worst pause does not grow with volume: it stays around 33–35 ms, about two frames. Quickshell reads the socket in chunks and returns control to the event loop between them. The daemon will still coalesce `unread.summary` (spec `daemon-api`), and the window will paginate.
3. **Large lines are not a problem.** 225 KiB on a single JSON line passes intact. No other framing is needed.
4. **Retries need backoff.** Every failed connection attempt leaves a `WARN quickshell.io.socket ... ServerNotFoundError` in the shell log. The real `Service.qml` must retry with exponential backoff (1 to 30 s) and stop trying while the daemon is intentionally off, so the log is not flooded.
5. **Writing is simple:** `write(json + "\n")` followed by `flush()`. No race between requests and notifications showed up.

## Spike limits

- It ran with `QT_QPA_PLATFORM=offscreen`, in a Quickshell separate from the real `omarchy-shell`. The event loop is the same kind, but inside the shell it competes with bar rendering. It will be measured again in M4.2, as a plugin.
- One client against one server. Several clients (TUI and shell at once) are tested in M2 with the real daemon.
